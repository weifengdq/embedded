## 6.4 工作原理

### 6.4.1 帧格式与四个阶段

I2C 的一次传输由四个阶段组成（RM §50.2.1，PDF p.855）：`START → 地址（+R/W）→ 数据（可多个）→ STOP`。
主机通过 `TRANSCTRL` 的 PHASE 位选择执行哪些阶段，这也是"地址扫描"能只用 START+ADDR+STOP 的原因。

- 7 位地址：1 字节 = 地址高 7 位 + R/W 位。
- ACK：从机把 SDA 拉低；NACK 则 SDA 保持高（由主机的上拉电阻维持）。
- 时钟由主机产生，但从机可以通过**拉低 SCL** 延展时钟（clock stretching），主机必须等。

### 6.4.2 时序参数与公式

RM `50.2.2（PDF p.856）给出 SETUP 寄存器各字段的计算公式（单位都是 I2C 功能时钟周期数，TPM 可放大）：

```text
毛刺过滤宽度   = T_SP × Clk_Period × (TPM + 1)                                  (6)
数据建立时间   = (2 × Clk_Period) + (2 + T_SP + T_SUDAT) × Clk_Period × (TPM + 1)  (7)
数据保持时间   = (2 × Clk_Period) + (2 + T_SP + T_HDDAT) × Clk_Period × (TPM + 1)  (8)
SCL 高电平     = (2 × Clk_Period) + (2 + T_SP + T_SCLHI) × Clk_Period × (TPM + 1)  (9)
SCL 低电平     = (2 × Clk_Period) + (2 + T_SP + T_SCLHI × T_SCLRATIO) × Clk_Period × (TPM + 1) (10)
```

驱动 `i2c_configure_timing()` 按模式查表（100k: t_high=4.0 µs/t_low=4.7 µs；400k: 0.6/1.3 µs；
1M: 0.26/0.5 µs），再反解 `T_SCLHI` 等字段。功能时钟是 **80 MHz**（本板实测），
所以 `Clk_Period = 12.5 ns`，这些字段都是几十到几百的整数——**一旦整数截断就会偏离标称频率**，
这是本章最重要的待确认点（见第 11 节）。

### 6.4.3 引脚与复用：一个真实冲突

本板 I2C0 的 SCL=PC08，而 **PC08 同时是 MCAN2_TXD**（`init_mcan2_pins()`）。
同一根 PAD 只能选一个 ALT，所以 **I2C0 与 CAN2 不能同时工作**。本板 4 路 CAN 全用，
因此本章例程改用 **I2C1：SCL=PD13 / SDA=PD12**（这两个脚在本板未被其它功能占用）。

可用的 I2C 引脚组合（择一，均需外部上拉或使用内部上拉）：


表 6-3 I2C 相关寄存器与驱动 API 对照

| 实例 | 引脚组合 | 本板占用情况 |
|---|---|---|
| I2C0 | PC08(SCL)/PC09(SDA) 或 PD08/PD09 | PC08 与 CAN2_TXD 冲突；PD08 是 ESC EEPROM 脚 |
| I2C1 | **PD13/PD12**（本章）或 PC13/PC12、PF13/PF12 | PC13/PC12 是 SPI1 MOSI/MISO；PF13/PF12 是 RGMII |
| I2C2 | PB02/PB03 或 PD03/PD02、PC03/PC02 | PD02/PD03 是 PWM0 输出；其它可用 |

> 结论：**优先用 I2C1(PD13/PD12)**；需要第二路时用 I2C2(PB02/PB03)。

扫描核心只有一句"纯 probe"：

```c
/* size=0 表示只做地址阶段: START + 地址 + ACK + STOP */
hpm_stat_t st = i2c_master_write(T_I2C, addr7, &dummy, 0U);
```

表 6-11：引脚电气自检结果（i2c_soft_selftest）。

| 测试项 | SCL(PD13) | SDA(PD12) | 结论 |
|---|---|---|---|
| 输入 + 内部下拉 → DI | 0 | 0 | PASS（DI 通路正常） |
| 输入 + 内部上拉 → DI | 1 | 1 | PASS（内部上拉有效） |
| 输出（开漏）驱动 0 → DI | 1 | 1 | 注意：DI 不反映输出低电平 |
| 输出释放 → DI | 1 | 1 | 高（上拉） |

由表 6-11 得到一个与直觉相反的结论：本 SoC 的 GPIO 在开漏输出模式下，
**DI 读回的是引脚外部真实电平而不是 DO**——驱动 0 时若外部没有从机/上拉回路把线拉低，DI 仍读到 1。
因此软件 I2C 的自回读验证不可行，必须靠外部上拉 + 从机真实驱动（或示波器）。
另外：软件扫描 112 个地址全 NACK（板上无从器件）；9 时钟恢复后 SCL/SDA 均回到高电平，说明开漏+上拉在空闲态正常。

| A | PD02 推挽输出 0 | PD07 = 0（线被拉低） | PD02 DI = 1 |
| B | PD02 开漏输出 0（OD=1） | PD07 = 0（**开漏拉低有效**） | PD02 DI = 1 |
| C | PD02 开漏释放（写 1） | PD07 = 1 | PD02 DI = 1 |
| D | PD07 开漏输出 0 | PD02 = 1（PD02 此时仍是输出态） | PD07 DI = 1 |

结论：**开漏本身工作正常**——对端引脚能读到 0，说明管子确实把线拉低了；
读不到 0 的是"自己的 DI"。GPIO 在输出态（OE=1）下 DI 不跟随引脚电平，恒读到 1，
所以"驱动 0 再读自己的 DI"不能用来判断开漏是否生效。自检开漏要用另一个引脚读（用例 A/B），
或把本脚切回输入态再读——这也是软件 I2C 里"释放总线后读 ACK"必须先切输入的原因。

**与 MCAL 版对照（2026-11-02 补充）**：同一块板上，MCAL 版 I2C 例程在 400 kHz 读方向曾经 100% 失败
（读回字节被采样成 0x00），而本章这个芯片级例程一直正常。原因是本章例程从头到尾让从机 I2C3 保持
标准模式（normal）时序，`SETUP.T_SUDAT = 12`（数据建立时间 250 ns）；MCAL 版每次切速率都会把从机
也重配成 fast 时序，SDK 在 fast/fast_plus 下把 `T_SUDAT` 算成 0（100 ns，正好是快速模式规范下限、
没有余量），从机发送方向就被控制器采样错了。修复在 mcal/I2c（把目标通道 T_SUDAT 抬到 250 ns 下限），
芯片级结论不受影响。控制变量实验与最终数据见第 46 章 §46.8.5 表 46-10。

## 6.8 性能与调优

1. **一次传输的数据量受 FIFO 限制（4 字节）**，超过就要靠"分块 + 中断/DMA"；
   如果你要读 128 B EEPROM，正确做法是 DMA（`i2c_master_start_dma_read()`）或每 4 B 一次中断。
2. 地址扫描的软件开销可用"重试次数"优化：扫描前把 `HPM_I2C_DRV_MASTER_ADDRHIT_RETRY_COUNT` 调小，
   扫描 112 个地址能从 84 ms 降到几 ms（需要改驱动宏，本仓库未改，属优化建议）。
3. 400k/1M 速率对**上拉电阻与总线电容**敏感：内部上拉（几十 kΩ）只适合短距离、低速率；
   400k 以上建议外部 2.2~4.7 kΩ。
4. 长线/多从机时给 SCL/SDA 加 TVS 或串阻，并保证从机 clock stretching 被正确处理
   （驱动的轮询方式默认会等待）。
5. 总线死锁（从机把 SDA 拉死）时用 `i2c_gen_reset_signal()` 发 9 个 SCL 时钟解锁（本章例程有 `i2c_reset` 命令）。

## 6.9 坑与注意事项

0. **现象：I2C 主机一个时钟都不发/从机永远不 ACK** → 原因：I2C 引脚（open-drain）必须打开 IOC 的 LOOP_BACK，
   否则控制器采不到自己的 SCL/SDA 反馈（本仓库实测：不开时全部 NACK/超时，加上 LOOP_BACK 后立刻 0 错误 PASS）。
   → 解决：见 `boards/hpm5e31_1/pins/pinmux_core.c` 的 `init_i2c2_master_pins()/init_i2c3_slave_pins()`。
10. **现象：I2C3 与 QEI 例程互相干扰** → 原因：PD06/PD07 同时被 `samples/qei/qei_gpio_sim` 当 GPIO 输出用。
    → 解决：两个例程不能同时初始化；各自单独跑没问题。
1. **现象：I2C0 初始化后 CAN2 不工作（或反之）** → 原因：PC08 同时是 I2C0_SCL 和 MCAN2_TXD。
   → 解决：用 I2C1(PD13/PD12) 或 I2C2(PB02/PB03)，见 2.3 节的引脚表。
2. **现象：扫描全部 NACK，以为芯片坏了** → 原因：板上没有从器件，NACK 是正确行为。
   → 解决：外接 AT24C128（0x50）或任何 I2C 传感器后重扫；或用示波器看 SCL/SDA 波形。
3. **现象：用 IOC LOOP_BACK 想把 SCL/SDA 短起来做回环** → 原因：LOOP_BACK 是"本 PAD 输出回送本 PAD 输入"，
   SCL 的回送不会跑到 SDA。→ 解决：真正回环需要**外部把两块板的 SCL-SCL、SDA-SDA 相连**，
   或者用两个 I2C 实例（一个主机一个从机）加外部连线。
4. **现象：400k/1M 下偶发 NACK/数据错** → 原因：内部上拉太弱、总线电容大、上升沿太慢。
   → 解决：加外部上拉 2.2~4.7 kΩ，缩短线长；必要时降到 100k。
5. **现象：I2C 传输卡住不返回** → 原因：从机拉低 SCL 做 clock stretching，或 SDA 被拉死。
   → 解决：驱动会轮询等待，超时后返回错误；恢复用 9 时钟复位。
6. **现象：改了 I2C 实例但完全不通信** → 原因：只改了 `HPM_I2Cx`，没改引脚复用和时钟
   （`board_init_i2c_clock()` 只支持 I2C0~3 且会调用对应 `init_i2cN_clock()`）。
   → 解决：按"实例 → 引脚 → 时钟 → i2c_init_master"四步核对。
8. **现象：软件 I2C 驱动 0 后读 DI 仍是 1** → 原因：开漏输出态下 DI 反映引脚真实电平，不是 DO；外部无上拉回路/从机时线不会被真正拉低（本板实测，见表 6-11）。
   → 解决：读 ACK/数据必须依赖从机真实驱动；只做时序验证时不要用 DI 自回读判断。
9. **现象：软件 I2C 设 1 MHz 实际只有约 1.5 MHz 且不稳** → 原因：CPU 周期级延时存在固定开销（函数调用+寄存器写），最小 10 周期已饱和，且中断会直接破坏时序。
   → 解决：软件 I2C 建议 ≤400 kHz，并用 `i2c_soft_timing` 实测校准；高速用硬件 I2C。
7. **现象：扫描 112 个地址要 84 ms，实时性差** → 原因：每次 NACK 都要空转 5000 次。
   → 解决：扫描时临时调小重试宏，或只扫已知地址段（如 0x50~0x57）。
