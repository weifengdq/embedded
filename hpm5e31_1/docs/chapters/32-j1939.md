## 32.3 概述：J1939 分层与文档体系

SAE J1939 是商用车（卡车/客车/工程机械）的 CAN 应用层标准族。它把 OSI 七层压成"物理层 + 数据链路层 + 应用层"三层，
再用一组子标准分别规定不同侧面。做嵌入式开发最常打交道的四个子标准见**表 32-1**。

| 子标准 | 名称 | 管什么 | 本实现覆盖 |
|---|---|---|---|
| J1939-21 | 数据链路层 | 29 位 ID/PGN 编解码、请求/应答、BAM、RTS/CTS 传输协议 | 完整（不超过 1785 B） |
| J1939-71 | 车辆应用层 | 各 PGN 的信号定义、周期、优先级、字节序 | EEC1/ET1/CCVS1/LFE |
| J1939-73 | 诊断应用层 | DM1/DM2/DM3/DM11、SPN/FMI/OC、灯状态 | 完整（单帧 DM1 + 多包 DM2） |
| J1939-81 | 网络管理 | NAME、地址声明、地址冲突、SA 分配 | 完整（含任意地址能力） |

表 32-1 J1939 四个核心子标准与本项目的覆盖范围

和 CANopen 的"对象字典 + PDO/SDO"、UDS 的"服务 + 会话"不同，J1939 的哲学是**面向信号、周期广播**：
发动机转速这种信号每 10 ms 主动广播一次，谁需要谁监听；诊断和长数据传输才用请求/应答。
这决定了 J1939 的实时性是"带宽 + 优先级"换来的，而不是"轮询"换来的。

典型应用：整车动力总成网络（发动机、变速箱、ABS、仪表）、车队远程诊断（DM1 故障灯）、
工程机械的 J1939 网关。本书的 `j1939_ecu` 例程就是一台"最小发动机 ECU"：地址声明 + 周期信号 + 故障灯。

## 32.4 工作原理

### 32.4.1 29 位 ID 与 PGN

J1939 只使用 29 位扩展帧。ID 的位域划分见**图 32-1**：Priority(3) / EDP(1) / DP(1) / PF(8) / PS(8) / SA(8)。
PGN 是从 ID 中"抠掉优先级和源地址"后剩下的 18 位，但 PS 段是否参与 PGN 取决于 PF：

- PF 小于 240（PDU1）：PS 是**目的地址 DA**，不参与 PGN，例如地址声明 PGN 0x00EE00、请求 PGN 0x00EA00、TP.CM 0x00EC00；
- PF 大于等于 240（PDU2）：PS 是**组扩展 GE**，参与 PGN，例如 DM1 0x00FECA、EEC1 0x00F004。

![图 32-1 29 位 ID 位域与 PGN 计算（PDU1/PDU2 对比）](figures/32/fig-32-1-j1939-id.png)

图 32-1 29 位 ID 位域与 PGN 计算；同一段 PS 在 PDU1 里是目的地址、在 PDU2 里是 PGN 的一部分

这个差别是后面所有"坑"的根源：**PDU2 报文没有目的地址字段**，所以"请求 EEC1"的应答仍然是广播，
主机不能用 DA 来区分"应答"和"周期帧"（第 33.10 节坑 6）。本项目把编解码集中在
`components/app_j1939/src/j1939_id.c`：

```c
uint32_t j1939_pgn_from_id(uint32_t id)
{
    uint32_t pf = J1939_ID_PF(id);
    uint32_t ps = J1939_ID_PS(id);
    uint32_t pgn;

    if (pf < 240U) {                       /* PDU1：目的地址不参与 PGN */
        pgn = (J1939_ID_EDP(id) << 17) | (J1939_ID_DP(id) << 16) | (pf << 8);
    } else {                               /* PDU2：组扩展参与 PGN */
        pgn = (J1939_ID_EDP(id) << 17) | (J1939_ID_DP(id) << 16) | (pf << 8) | ps;
    }
    return pgn & 0x3FFFFUL;
}
```

优先级由 PGN 决定（应用可覆盖）。本书用到的 PGN 与默认优先级见**表 32-2**。

| PGN | 名称 | 方向/用途 | 默认优先级 | 周期 |
|---|---|---|---|---|
| 0x00E800 | ACK | 应答确认（0=ACK 1=NAK） | 6 | 事件 |
| 0x00EA00 | Request | 请求某 PGN | 6 | 事件 |
| 0x00EB00 | TP.DT | 传输协议数据包（1 序号 + 7 字节） | 7 | 事件 |
| 0x00EC00 | TP.CM | 连接管理：BAM/RTS/CTS/EOMA/Abort | 7 | 事件 |
| 0x00EE00 | Address Claimed | 地址声明（8 字节 NAME） | 6 | 上电/冲突 |
| 0x00F004 | EEC1 | 发动机转速/扭矩 | 3 | 10 ms |
| 0x00FEEE | ET1 | 冷却液/机油温度压力 | 6 | 1 s |
| 0x00FEF1 | CCVS1 | 车速/制动/巡航 | 6 | 100 ms |
| 0x00FECA | DM1 | 激活故障 + 灯状态 | 6 | 1 s |
| 0x00FECB | DM2 | 历史故障 | 6 | 请求 |
| 0x00FECC / 0x00FED3 | DM3 / DM11 | 清除历史 / 清除激活 | 6 | 请求 |

表 32-2 本书覆盖的 PGN、优先级与周期（J1939-71 附录 A、J1939-73）

### 32.4.2 网络管理：NAME 与地址声明

每个 J1939 节点有一个 64 位 NAME，作为"身份指纹"；源地址 SA 是"门牌号"，可以由协议自动分配。
NAME 的位域见**表 32-3**。注意：题目材料里写的"21 字节"是笔误，标准 NAME 是 8 字节 / 64 位，
其中包含 **21 位** Identity Number。

| 位 | 字段 | 宽度 | 本书取值（ECU） |
|---|---|---|---|
| [0] | Arbitrary Address Capable | 1 | 0（固定地址） |
| [3:1] | Industry Group | 3 | 0（On-Highway） |
| [7:4] | Vehicle System Instance | 4 | 0 |
| [14:8] | Vehicle System | 7 | 0 |
| [15] | Reserved | 1 | 0 |
| [23:16] | Function | 8 | 0 |
| [28:24] | Function Instance | 5 | 0 |
| [31:29] | ECU Instance | 3 | 0 |
| [42:32] | Manufacturer Code | 11 | 1 |
| [63:43] | Identity Number | 21 | 0x000123 |

表 32-3 NAME 位域（J1939-81 4.1 节）；本书 ECU 的 NAME = 0x0009180100000000

地址声明状态机见**图 32-2**。上电后节点**不能立刻用自己的 SA 发周期报文**，否则会和同地址节点打架：

1. 用 SA=0xFE（空地址）广播"请求地址声明"（PGN 0xEA00，数据为 0xEE00 三字节小端）；
2. 等 250 ms（标准允许 250 ms~2.5 s，本书取最小值便于测试仪判定），收集同 SA 的声明；
3. 若无冲突，用自己的 SA 广播 Address Claimed（PGN 0xEE00 + 8 字节 NAME），状态进入 CLAIMED；
4. 若收到**同 SA 且 NAME 更小**的声明，则自己输：有任意地址能力就换一个地址并重新请求；
   没有就发 SA=0xFE 的声明表示"无法声明"，此后只能收不能发。

![图 32-2 地址声明状态机（J1939-81 4.3 节）](figures/32/fig-32-2-addr-claim.png)

图 32-2 地址声明状态机：请求 → 250 ms 等待 → 广播 NAME；冲突时换址或退到 0xFE

实测地址声明耗时 **251.167 ms**（250 ms 等待 + 帧时间 + 轮询粒度），见
`logs/20261030-170249-j1939_ecu.log`；测试仪在 CAN1 上按 PGN/SA 校验 NAME 一致后才算 PASS。

地址冲突用例（2026-11-02 新增，`conflict` 命令）：把两个节点都设成 `preferred_sa=0x80`、NAME 分别 0x10000 / 0x20000，
跑两相——第一相输者支持动态换址（NAME bit0=1），应换到 0x81 并重新声明；第二相输者不支持（bit0=0），
应退到 0xFE 且 `addr_state=CANNOT_CLAIM`。测完自动恢复默认配置，可以接着跑 `run`。

2026-11-02 上板结果（`logs/20261102-123406-j1939_ecu.log`）：

```text
phase1(输者arb=1): A(CAN0,name=1000012300010003) sa=0x80 state=2 | B(CAN1,name=0800012300010003) sa=0x80 state=2 | claims_rx A=3 B=2
phase2(输者arb=0): A(CAN0,name=1000012300010002) sa=0xFE state=3 | B(CAN1,name=0800012300010003) sa=0x80 state=2 | claims_rx A=2 B=2
```

phase2 符合预期：输者不支持动态换址，退到 `sa=0xFE`、`state=3`（CANNOT_CLAIM），赢者保持 0x80。
**phase1 不符合预期**：输者 A 的 NAME 更大（0x1000… > 0x0800…），本应换到 0x81，结果两个节点都停在 0x80。

根因在换址与等待的衔接处。`claim_choose_next()` 只改了 `s->sa`，而 `claim_restart()`
之后等待 250 ms 的"声明成功"分支写的是 `s->sa = s->cfg.preferred_sa` —— 还是原来的 0x80，
刚选好的新地址被覆盖回去，于是永远换不走。修复只有一行：在 `claim_choose_next()` 里
把 `cfg.preferred_sa` 一起改掉；这样等待期结束后声明的是新地址，也不会再和赢者撞。
改完后 `j1939_ecu` 重编通过（FLASH 106.4 KB），再跑一次同一个用例
（`logs/20261102-124356-j1939_ecu.log`）：

```text
phase1(输者arb=1): A(CAN0,name=1000012300010003) sa=0x81 state=2 | B(CAN1,name=0800012300010003) sa=0x80 state=2 | claims_rx A=3 B=2
phase2(输者arb=0): A(CAN0,name=1000012300010002) sa=0xFE state=3 | B(CAN1,name=0800012300010003) sa=0x80 state=2 | claims_rx A=2 B=2
```

phase1 现在符合 J1939-81：输者换到 0x81 并保持 CLAIMED，赢者留在 0x80；phase2 仍是退 0xFE。
同一份固件的 9 项回归（地址声明/周期/请求应答/DM1/DM2/DM11）也全 PASS。

### 32.4.3 传输协议：BAM 与 RTS/CTS

单帧 8 字节装不下 DM2 历史故障（2+4×N）或标定数据，J1939-21 用**两条 TP.CM 报文 + 最多 255 个 TP.DT** 拼起来：

- **BAM（Broadcast Announce Message，0x20）**：广播，无流控、无确认，最后一个 DT 到达即完成；
  标准规定包间隔 50 ms 以上，所以 500 字节要 72 包约 3.6 s，有效吞吐只有 **140.8 B/s**。
- **RTS/CTS（0x10/0x11/0x13/0xFF）**：点对点，接收方用 CTS 给"窗口"（本次允许发几包），
  发送方发完窗口再等下一个 CTS，全部收完后接收方回 EOMA。窗口可以背靠背发，本实现 CTS 包间隔默认 1 ms，
  500 字节只需 **72.8 ms（6867.9 B/s）**，是 BAM 的 **49 倍**。

时序对比见**图 32-3**，超时定义见**表 32-4**。

![图 32-3 BAM 与 RTS/CTS 时序对比（含实测包间隔与吞吐）](figures/32/fig-32-3-tp-timing.png)

图 32-3 BAM 固定 50 ms 包间隔；RTS/CTS 用窗口背靠背传输，吞吐高 49 倍

| 定时器 | 值 | 管什么 | 本实现落点 |
|---|---|---|---|
| T1 | 750 ms | RTS/CTS 收到 CTS 后等第一个 DT；BAM 接收方包间超时 | `j1939_tp.c` 接收会话 deadline |
| T2 | 1250 ms | 发送方发 RTS 后等 CTS | `J1939_T2_MS`，`tx->deadline_ms` |
| T3 | 1250 ms | RTS/CTS 包间/等下一个 CTS | `J1939_T3_MS` |
| T4 | 1050 ms | 发完最后一包后等 EOMA | `J1939_T4_MS` |

表 32-4 TP 超时（J1939-21 5.10.4 节）与代码位置

一个容易漏掉的实现细节：**接收方收满一个窗口后必须主动再发 CTS**，否则发送方会卡在 T3 超时。
本项目在收到第 16 个 DT 时续发下一个 CTS（`j1939_tp.c`）：

```c
if (!rx->bam) {
    if (rx->cts_left > 0U) {
        rx->cts_left--;
    }
    if (rx->cts_left == 0U) {
        uint16_t remain = (uint16_t) (rx->npackets - (rx->next_seq - 1U));
        uint8_t win = (remain > 16U) ? 16U : (uint8_t) remain;
        rx->cts_left = win;
        cm_send(s, rx->src, J1939_TP_CM_CTS, rx->total_len,
                (uint8_t) rx->npackets, win, rx->pgn);
    }
}
```

### 32.4.4 诊断报文 DM1/DM2/DM3/DM11

DM1（PGN 0xFECA）每秒广播一次"当前有没有故障、哪个灯亮"。布局见**图 32-4**：
第 1 字节是 4 个灯各 2 bit（MIL/RSL/AWL/PL，0=灭 1=亮 2=错误 3=不可用），第 2 字节是闪灯状态，
之后每个 DTC 占 4 字节：SPN 19 位 + FMI 5 位 + OC 7 位。解码公式：

    SPN = (b0 & 7) | (b2 << 3) | (b3 << 11) | ((b1 >> 7) << 19)
    FMI = b0 >> 3
    OC  = b1 & 0x7F

![图 32-4 DM1 报文布局：灯状态字节与 DTC 4 字节位域](figures/32/fig-32-4-dm1-layout.png)

图 32-4 DM1 的灯字节与 DTC 编码；实测 SPN=100/FMI=4/OC=1 编码为 24 01 0C 00

- **DM2（0xFECB）**：历史故障，格式同 DM1，但可以带多个 DTC（本实现超过 8 字节时自动走 RTS/CTS）；
- **DM3（0xFECC）**：测试仪请求清除"历史故障"；
- **DM11（0xFED3）**：测试仪请求清除"激活故障"，灯随之熄灭，但历史仍保留（DM2 还能查到）。

`j1939_dm.c` 里 DTC 编码只有 4 行，但方向不能错：SPN 的低 3 位被塞进 FMI 字节的低 3 位，
第 20 位（bit19）藏在 OC 字节的最高位。这也是很多第三方工具解出来 SPN 少 8 倍的原因。

### 32.4.5 周期 PGN 调度与优先级

周期报文用毫秒时基轮询发送，**以当前时刻为基准**重算下一次（`next = now + period`），
避免 `next += period` 在长跑后越漂越远。`j1939_poll()` 建议 1 kHz 以上调用；10 ms 的 EEC1
在 1.5 s 内实测 150 帧、平均间隔 10000 us、最大 11492 us（抖动 +1.5 ms），见
`logs/20261030-170249-j1939_ecu.log`。

优先级不是"想设多少设多少"：EEC1 用 3（安全相关、周期短），ET1/CCVS1/DM1 用 6，TP 用 7。
总线上同时有 10 ms 周期帧、故障帧和 TP 大包时，优先级决定谁先赢仲裁——这是 J1939 没有"重传保证"时
保证实时性的唯一手段。

## 32.8 性能与调优

**吞吐**：250 kbit/s 总线上，8 字节经典帧（含填充约 130 bit）理论极限约 240 帧/s。
BAM 被 50 ms 包间隔锁死在 20 帧/s，所以有效载荷只有 140 B/s；
RTS/CTS 用 1 ms 间隔 + 16 包窗口，能跑到 6.8 KB/s（约 138 帧/s），
已接近"TP 每包 7 字节 + 帧头"的实际上限。把 `cts_gap_ms` 调 0 还能更快，但会挤占周期报文，
本项目保留 1 ms 让 EEC1（10 ms）仍能准点。

**抖动**：EEC1 平均 10000 us、最大 11492 us。偏差来源按影响排序：
一是串口 shell 轮询与 printf（921600 波特，一行 40 字节约 0.4 ms）；
二是 `j1939_poll()` 每轮最多收 32 帧，TP 大包突发时会把一次轮询拉长；
三是 MCAN 发送阻塞重试。
优化手段：把周期调度放 GPTMR 中断置标志（第 15 章）、TP 收发放独立状态机并限制每轮处理帧数、
热路径日志用环形缓冲而不是 printf。

**CPU 与内存**：协议栈无动态内存，单个节点结构体约 9 KB（含 2 个 1785 字节 TP 会话和重组缓冲），
两个节点镜像 98 KB Flash、32 KB DLM。`j1939_poll()` 空转一次约 2~3 us（不含收发）。

**优先级反转**：TP 数据包优先级 7（最低），如果在发 500 字节 BAM 时突然有 DM1（优先级 6）要发，
DM1 会先赢仲裁，BAM 包间隔被拉长——这符合标准，但会让接收方 T1 计时更紧张。
调优办法是给关键 TP（如诊断刷写）显式提优先级，而不是改全局。

**与内核栈的兼容性**（本轮逐一核对了内核源码，修正了上一版的错误结论）。

先说实测：内核 can-j1939 发的地址声明（0x18EEFF30）、RTS（TP.CM 0x10）、BAM 都能被本项目解码；
**RTS/CTS 点对点传输失败，内核回 Abort reason=5（FAULT）**。上一版把原因写成"标准与内核不一致"，
这个说法是错的。对照内核 `net/can/j1939/transport.c` 后，两边 CTS 的真实布局是：

| 字段 | J1939-21 / 内核 `j1939_session_tx_cts()` | 本项目 `j1939_tp.c: cm_send(CTS)` |
|---|---|---|
| byte0 | 0x11（TP.CM_CTS） | 0x11 |
| byte1 | 本次允许发送的包数 | 总长度低字节 |
| byte2 | 下一包序号（内核只解析这一字节） | 总长度高字节 |
| byte3 | 0xFF（J1939-21 里是下一包序号的中字节） | 总包数 |
| byte4 | 0xFF（高字节） | 窗口（本项目扩展） |
| byte5..7 | PGN（内核统一用 `j1939_xtp_do_tx_ctl()` 写入） | PGN |

**表 32-11** ：CTS 字段布局对照（内核 v6.12，`transport.c` 911~949 行；本项目 `j1939_tp.c` 64~79 行）。
两行的字节归位如图 32-5 所示，红/蓝两格就是冲突点。

![图 32-5 TP.CM CTS 字段布局对照](figures/32/fig-32-5-cts-layout.png)

**图 32-5** ：上行是 J1939-21 与 Linux can-j1939 的 CTS 布局，下行是本项目的 `cm_send()`。
byte1/byte2 一个写"允许包数/下一包号"、一个写"总长度低/高字节"，这就是内核取消会话的原因。
脚本 `tools/figs/app32_cts_layout.py`，字段取值来自两边源码，不是示意图。

问题出在第 1、2 字节：本项目把"总长度"塞进 byte1/byte2，内核读出来就是"允许包数 = 总长低 8 位"、
"起始包号 = 总长高 8 位"。传 500 B 时 byte2=0x01（看着像包号 1，勉强能过），
传 1000 B 以上 byte2 变成 0x03、总包数的值又被当窗口，双方窗口和序号立刻对不上，内核按错误序列取消会话。

内核的 RTS 还有一处自己的简化：`j1939_session_tx_rts()` 把 byte4（每 CTS 最大帧数）直接填成总包数，
而不是声明一个窗口大小。本项目接收内核 RTS 时把 byte4 当作窗口上限 clamp，
由于内核填的总包数 ≥ 本项目 16 包窗口，这处差异不影响接收侧。

**适配方案**（本轮没改码，原因见下）：`cm_send()` 里给 CTS 加一个分支，按上表右列改成
`data[1]=window、data[2]=next_seq&0xFF、data[3]=data[4]=0xFF、data[5..7]=PGN`；
发送侧解析 CTS 时改成 `window=data[1]、next_seq=data[2]`（现在读的是 `data[4]` 窗口、完全没读包号）；
接收侧续发 CTS 时把下一个期望包号写进 byte2。改动约 15 行，三个例程要重编。
验证命令：主机 `modprobe j1939` + `ip link set vcan0 up type can bitrate 250000`，
板端跑 `j1939_tp`，主机 `python3 host/j1939/hoststack_interop.py --channel vcan0 --mode rts`，
判据是内核不再回 Abort、板端 `tp_done_tx` 递增。本轮板卡窗口紧张（8 人共享队列），
没有足够时间重编 3 个例程并在 vcan 上双向复测，作为已知限制留给下一轮。

结论：**帧格式（29 位 ID/PGN/TP.DT 序号/7 字节载荷）兼容，TP.CM 的 CTS 控制字段不兼容**；
BAM 路径两边一致，可以互通。跨栈联调前先用 `candump` 抓 CTS 核对第 1、2 字节。

## 32.10 坑与注意事项

1. **过滤器掩码按 PF/PS，不按整 ID**：J1939 同一 PGN 的 SA 可变，硬件过滤器要屏蔽 SA 位
   （mask 0x00FFFF00 只比 PF/PS），否则换一个源地址就收不到。本书例程先用"接受所有扩展帧 + 软件过滤"，
   量产再收敛。注意 PDU1 的 PS 是 DA，按 DA 过滤要额外区分。
2. **BAM 包间隔与接收方缓冲**：标准要求 BAM 每包 50 ms 以上，接收方至少要能缓存"两包间隔内到达的帧"。
   若接收方被长任务阻塞超过 T1（750 ms），会话会超时，后续包因序号不连续被丢弃
   （实测：停摆 2.6 s 后 done_rx 不增加、timeout 计数 +1，恢复后重传正常）。
3. **优先级反转**：TP（优先级 7）被周期报文和诊断帧抢占，包间隔被拉长；35 个待发帧排队时
   可能触发接收方 T1。解决：关键传输提优先级，或缩短窗口让接收方有喘息。
4. **SA 冲突**：两个节点用同一 SA 且都没做地址声明时会互相覆盖。必须实现"请求、等待、声明"，
   并处理 NAME 更小者胜出的规则；否则总线上会出现两个 SA=0x00 的 ECU。
5. **未声明就发周期报文**：本实现在地址声明完成前**门控调度器**（`can_tx = addr_state == CLAIMED`），
   这是 J1939-81 的要求，也是调试时"为什么没有 EEC1"的常见原因。
6. **PDU2 没有 DA**：请求 ET1 的应答仍是广播帧，主机不能用 DA 区分应答与周期帧。
   本项目的做法是"请求后 80 ms 内到达同 PGN 即视为应答"（`j1939_ecu` 的 `tester_rx_cb`）。
7. **CTS 窗口续发**：接收方收满窗口不续发 CTS，发送方会卡到 T3 超时。第 32.4.3 节给出了续发代码，
   这是本项目 RTS/CTS 500 B 从 FAIL 变 PASS 的关键修复。
8. **DM1 单帧只装 1 个 DTC**：J1939-73 允许一条 DM1 只带一个 DTC，多故障时按严重度上报或改用 DM2 多包；
   把 2 个 DTC 硬塞进 8 字节会得到解析器看不懂的残包。
9. **0xFF 填充不是 DTC**：没有故障时 DM1 只有 2 字节（灯 + 闪灯）；解析器若把 FF FF FF FF
   当 DTC，会解出 SPN=0x7FFFF/FMI=31/OC=127 的假故障（`dm1_decode.py` 已过滤）。
10. **CAN FD / J1939-22 差异**：J1939-22 用 CAN FD 的 64 字节帧重写了传输层（单帧最多 60 字节、
    新增 ETP），ID 位域仍兼容但 TP.CM 控制字不同。本项目只做经典 J1939-21；
    同一总线混跑经典节点和 FD 节点会导致错误帧，需要用独立通道或网关隔离。
11. **内核栈 CTS 字段差异**（第 33.9 节）：Linux can-j1939 的 CTS 与标准不同，跨栈联调务必先抓包核对。

## 32.11 优劣评价与同类对比

J1939 与本书另外几个协议方向（CANopen、UDS/ISO-TP、XCP）常在同一台车上共存，**表 32-9** 给出横向对比。

| 维度 | J1939（-21/-71/-73/-81） | CANopen | UDS on ISO-TP | XCP on CAN |
|---|---|---|---|---|
| 寻址 | PGN + 源/目的地址，29 位 ID | 7 位节点号 + 对象字典索引 | 物理/功能地址（11/29 位） | CMD/RES 两个 ID |
| 大数据 | BAM（50 ms/包）或 RTS/CTS（窗口） | SDO 分段（握手） | ISO-TP（FF/CF/FC） | 块传输 |
| 实时性 | 周期广播 + 优先级仲裁，强 | PDO 事件/同步，强 | 诊断非实时 | 测量非实时 |
| 诊断 | DM1/DM2 故障灯 + SPN/FMI/OC | EMCY + 厂商对象 | 0x19/0x14 等服务 | 无 |
| 组网管理 | 地址声明（NAME 仲裁） | NMT + 心跳 | 无 | 无 |
| 典型领域 | 商用车/工程机械 | 工业/机器人 | 售后诊断/刷写 | 标定测量 |
| 本板实测 | 140.8 B/s（BAM）、6867.9 B/s（RTS/CTS） | 见第 33 章 | 见第 29/30 章 | 见第 34 章 |

优点：面向信号、天然支持多厂商组网（NAME + 地址声明）、诊断标准统一（一个 DM1 全车通用）、
优先级机制让安全信号有确定时延。缺点：带宽利用率低（BAM 50 ms 包间隔是硬伤）、
没有确认重传（BAM 丢包只能等下一周期）、PDU1/PDU2 的 DA 歧义容易写错、文档要买（SAE 收费，
公开资料只有摘要）。这也是为什么"能跑通 J1939 的 MCU 很多，能把 TP 和 DM 写对的少"。
