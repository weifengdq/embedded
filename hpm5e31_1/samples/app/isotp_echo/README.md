# isotp_echo —— ISO-TP(ISO 15765-2:2016) 回显节点 + 板内双节点闭环自测

> 源码仓库（公开镜像，暂定）：<https://github.com/weifengdq/embedded>；本书章节与实测日志见仓库 hpm5e31_1/docs/ 目录。

## 1. 这是什么

一颗 MCU 上同时跑 **ISO-TP 服务端（DUT）** 和 **ISO-TP 测试节点（tester）**：

| 角色 | CAN 通道 | 收 ID | 发 ID | 说明 |
|---|---|---|---|---|
| DUT | CAN0 | 0x700 | 0x708 | 收到一条完整 ISO-TP 消息后原样回显 |
| tester | CAN1 | 0x708 | 0x700 | 发请求、收回显、逐字节 CRC32 校验 |

CAN0 与 CAN1 在板上经 TCAN1044AV 接到同一段总线（两端 120 Ω 已接），
所以这是**真实的 CAN 总线收发**，不是单节点自环 —— BS/STmin/FC 的交互只有两个节点才能验证。

组件：`components/app_isotp/`（`app_isotp.c` 协议栈 + `app_isotp_port.c` SDK MCAN 端口）。

## 2. 接线

无需外接线。板载：

```
CAN0 PD00/PD01 ── TCAN1044AV ──┐
                               ├── 同一段 CAN 总线（板上 CAN0 ↔ CAN1 两两相连，120 Ω×2）
CAN1 PD05/PD04 ── TCAN1044AV ──┘
```

## 3. 命令

| 命令 | 作用 |
|---|---|
| `run` | 1/7/8/12/64/256/1024/4095 字节回显，CRC32 校验 + RTT + 吞吐 |
| `bench` | BS=0/8/32 × STmin=0/1ms/100us 参数扫描（其余参数固定） |
| `thr [n]` | 4095 B 连续回显 n 次，测稳定吞吐 |
| `fd` | 切到 CAN FD（仲裁 1 Mbit/s / 数据 2 Mbit/s，BRS，TDC）复测 |
| `ext` | 切到 29 位 ID（0x18DAF110 / 0x18DA10F1）复测 |
| `pad [b]` | padding 字节验证，默认 170(0xAA)；打印最后一帧尾部字节 |
| `stat` | 协议栈统计（帧数/FC 数/序号错/溢出/超时） |
| `info` | 当前模式、ID、BS/STmin/pad、N_Bs/N_Cr |

上电 1.5 s 后自动执行一次 `info;run`，因此 `hwrun.sh` 不加 `--send` 也有 PASS 证据。

## 4. 实测数据（2026-10-30，HPM5E31 @480 MHz，XIP）

日志：

- `logs/20261030-165808-isotp_echo.log`（classic + FD + 29 位 + padding + stat，**主证据**）
- `logs/20261030-165657-isotp_echo.log`（classic + BS/STmin 扫描 27 组）
- `logs/20261030-165559-isotp_echo.log`（首轮 PASS）

### 4.1 经典帧 500 kbit/s（11 位 ID，BS=0，STmin=0，pad=0xCC）

| 长度 B | 回显帧数 | RTT µs | 双向吞吐 KB/s | 发送耗时 µs | CRC |
|---|---|---|---|---|---|
| 1 | 1 | 526 | 3.7 | 227 | OK |
| 7 | 1 | 462 | 29.6 | 227 | OK |
| 8 | 2 | 1429 | 10.9 | 701 | OK |
| 12 | 2 | 1411 | 16.6 | 698 | OK |
| 64 | 10 | 5145 | 24.3 | 2556 | OK |
| 256 | 37 | 17727 | 28.2 | 8814 | OK |
| 1024 | 147 | 69031 | 29.0 | 34357 | OK |
| 4095 | 586 | 273505 | 29.2 | 136100 | OK |

结论：**8/8 全 PASS，seq_err=0 ovflw=0 timeout=0**。
4095 B 用了 586 帧（1 FF + 585 CF），RTT 273.5 ms，已经贴近 500 kbit/s 的物理上限：
每个 8 字节经典帧约占 108 bit（含帧间隔）→ 586×108/500k ≈ 126 ms 单向，双向 253 ms，实测 273.5 ms（含软件处理 ~8% 开销）。

### 4.2 CAN FD 1 Mbit/s / 2 Mbit/s（64 字节帧）

| 长度 B | 回显帧数 | RTT µs | 双向吞吐 KB/s | 对比经典 |
|---|---|---|---|---|
| 1 | 1 | 170 | 11.5 | — |
| 7 | 1 | 167 | 81.9 | — |
| 8 | 1 | 209 | 74.8 | **8 B 只占 1 帧**（SF 转义形式） |
| 12 | 1 | 240 | 97.7 | 1 帧 vs 经典 2 帧 |
| 64 | 2 | 982 | 127.3 | 5.2× |
| 256 | 5 | 2913 | 171.6 | 6.1× |
| 1024 | 17 | 10756 | 185.9 | 6.4× |
| 4095 | 66 | 42188 | 189.6 | **6.5×** |

FD 29 位 ID 复测：4095 B RTT 44598 µs、179.3 KB/s、8/8 PASS（`29-bit evidence: cli tx_id=0x18DAF110 ext=1`）。

### 4.3 BS/STmin 扫描（经典 500 kbit/s，1024 B）

| BS | STmin | RTT µs | 双向 KB/s |
|---|---|---|---|
| 0 | 0x00 (0 µs) | 69031 | 29.0 |
| 0 | 0x01 (1 ms) | 291422 | 6.9 |
| 0 | 0xF1 (100 µs) | 69031 | 29.0 |
| 8 | 0x00 | 77391 | 25.8 |
| 8 | 0x01 | 272172 | 7.3 |
| 8 | 0xF1 | 77237 | 25.9 |
| 32 | 0x00 | 70880 | 28.2 |
| 32 | 0x01 | 287151 | 7.0 |
| 32 | 0xF1 | 70898 | 28.2 |

解读：

1. **STmin=1 ms 直接把吞吐压到 1/4**（7 KB/s vs 29 KB/s）—— 1024 B 需要 147 帧，147×1 ms = 147 ms，
   单向就 147 ms，与实测 291 ms(RTT) 吻合，说明本实现的 STmin 计时是准的。
2. **STmin=0xF1（100 µs）与 STmin=0 无差别**：因为每帧本身在 500 kbit/s 上就要 176~216 µs，
   100 µs 的最小间隔被物理层"吸收"了。这就是 ISO-TP 的 STmin 只能是**下限**、不能提速的原因。
3. **BS=8/32 比 BS=0 慢 5~12%**：每块结束要等一个 FC，多一次往返（230 µs）+ 软件处理。
   BS=0（不分块）在点对点诊断里最快，但长消息会长时间占用接收方缓冲。

### 4.4 padding

`pad 170` 输出：

```
[isotp_echo] pad test: pad=0xAA last_frame_len=8 tail=AA AA AA AA AA -> PASS(经典帧固定 8 字节)
```

64 B 消息的最后一个 CF 只有 2 字节有效载荷，尾部 5 字节被填成 0xAA —— 说明 padding 真的上了总线，
不是只在软件里拼的。

## 5. 坑

1. **MCAN 的 `dlc` 字段是 DLC 编码不是字节数**。`tx.dlc = 16` 并不表示 16 字节，而是"DLC=16"（非法），
   帧根本发不出去；12 字节对应 DLC=9。本组件第一版就踩了这个坑：经典 8 字节恰好 dlc==字节数，
   一切正常，切到 FD 后 12/64/256/1024/4095 全部超时（`logs/20261030-165657` 的 FAIL 行是修复前证据）。
2. **单次 poll 的 CF 突发长度要限流**。HPM5E00 的 MCAN RX FIFO0 经典 32 元素、FD **只有 8 元素**；
   一次把几百个 CF 灌进 TX FIFO，对端还没轮到 poll 就溢出。本组件 `APP_ISOTP_DEFAULT_BURST=4`。
3. **板内双节点必须"平铺"调度**：不能让 tester 在阻塞发送里回调 DUT 的应答（会重入死锁），
   所以 ISO-TP 全部做成非阻塞状态机，主循环里 pump 两路 + poll 两个实例。
4. **hwrun 的串口采集比上电晚 ~0.3 s**，上电立刻 printf 会丢；例程里 `board_delay_ms(1500)` 后再自测。

## 6. 复现

```bash
cd hpm5e31_1
bash scripts/hwrun.sh app/isotp_echo --secs 30 --send "bench;fd;ext;pad 170;stat" --lock-wait 1800
```

期望最后看到 `[isotp_echo] PASS sizes=8/8 ...` 两到三次（classic / FD / 29 位各一次）。
