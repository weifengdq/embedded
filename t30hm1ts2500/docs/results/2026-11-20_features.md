## 0. 结论速览

| 特性 | 结论 | 关键实测 |
| --- | --- | --- |
| TC6 设备时间（PTPSEC/PTPNSEC） | ✅ 能用 | 5 次连读单调递增；`time set 1000 0` 后回读 1000.3679 s，2 s 后 1002.7288 s |
| TC6 发送时间戳（TTSC） | ⚠️ 部分 | TSC=1/2/3 均能捕获且与设备时间吻合，但**全部落在 TTSCC**，TTSCA/B 始终为 0 |
| TC6 接收时间戳（RTSA） | ⬜ 未测 | 打开 FTSE 会让驱动把前插时间戳当帧数据，需先改 recv 路径 |
| TC14 拓扑发现 | ✅ 能用（需静默总线+手动寄存器） | HPM↔TC387 双向成功：`TD_STAT=0xA000`、`DIST_MR≈18750`、`DLY_MR≈37900`（dur=16 ms） |
| TC14 封装命令 `s2500 td ref/meas` | 已修等待逻辑，复测受阻 | 原在 DLYM_DONE 提前返回（dist_mr=0）；现改为等 DM_DONE + 2*dur+10ms 稳定期，但封装命令轮询期间 HPM/TC387 均出现芯片复位，dist_mr 未能稳定复现 18750；**测距仍以手动寄存器为准**（2.3 节） |
| DIO/LED 功能码 | ✅ 寄存器可控 | `DIOCFG0` 0xCBDF→0x8B9F→0x9F8B→0x9991→0x8181，FN0/FN1 回读一致 |
| SQI | ⚠️ 有流量才有值 | 空闲 0/7、SQI+=7；并发 ping 时三板均 3/7、SQI+=119 |
| HDD | ⚠️ 三板一致报 SHORT_OPEN=2 | valid=1 ready=1 SHORT_OPEN=2 1W_SHORT=1（终端并联过量，非芯片故障） |
| TC10 睡眠/唤醒 | ⬜ 未实测（风险控制） | 见 §6：只给方案与恢复路径，未让芯片进入 Sleep |

## 1. TC6 时间戳

### 1.1 设备时间单调性（HPM5361）

```
host 1795146147.017177437  chip PTP time: 1779.548507384 s
host 1795146147.378221013  chip PTP time: 1779.926991304 s
host 1795146147.759265361  chip PTP time: 1780.296795944 s
host 1795146148.125602709  chip PTP time: 1780.662814824 s
host 1795146148.490778016  chip PTP time: 1781.035877864 s
host 1795146148.865734596
```

* 芯片时间 5 次读 Δ=1.48737 s，对应主机 Δ=1.47356 s（读命令前后各差一次串口往返），
  比值 ≈1.009；**单调递增、无回跳**，速率与主机一致（<1% 误差来自串口往返时刻，不是时钟偏差）。
* `PTPSEC` 是秒计数，回绕周期约 136 年，本测试不涉及回绕。

### 1.2 写时间

```
$ s2500 time set 1000 0
time set to 1000.000000000
PTP time: 1000.367923752 s
# sleep 2
PTP time: 1002.728833112 s
```

写 `SETSEC`/`SETNSEC(SETT=1)` 立即生效，之后从 1000 s 继续走，Δ=2.3609 s（主机侧 2 s + 两次串口往返）。

### 1.3 未开 FTSE / 无 TSC 时 TTSC 全 0（符合预期）

```
CONFIG0 = 0x00009806  [FTSE=0]
TTSCA = 0x0000000000000000
TTSCB = 0x0000000000000000
TTSCC = 0x0000000000000000
# ping 20 帧后
TTSCA/B/C 仍全 0；STATUS0=0x00000072
```

### 1.4 发送时间戳捕获（新增 `s2500 ts tx` 命令）

原 shell 没有任何路径给发送帧置 TSC 字段（`s2500_send(..., flags)` 只有 `bench` 用且传 0），
本次在 `common/s2500/s2500_shell.c` 增加：

```
s2500 ts tx <a|b|c> [len]   # 置 CONFIG0.FTSE, 发 60..1500B 广播帧(带 TSC), 等 STATUS0.TTSCAx, 读 TTSCx, 复原 CONFIG0
```

实测（HPM5361，60B，三次独立发送）：

| 发送命令 | 发送前设备时间 | STATUS0 | TTSCA | TTSCB | TTSCC | 解码（2-bit 秒 + 30-bit ns） | 对应绝对时间 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `ts tx a 60` | 148.290099624 s | 0x00000440 | 0 | 0 | 0x23467BB8 | sec=0, ns=591821752 | 148.5918 s |
| `ts tx b 60` | 151.145546104 s | 0x00000440 | 0 | 0 | 0xDAA0F808 | sec=3, ns=446922760 | 151.4469 s |
| `ts tx c 60` | 154.002698584 s | 0x00000440 | 0 | 0 | 0x921ED9E8 | sec=2, ns=304011752 | 154.3040 s |
| `ts tx c 60`（另一次） | 130.902360184 s | 0x00000440 | 0 | 0 | 0xCC2C0B78 | sec=3, ns=204213112 | 131.2040 s |

* 时间戳都落在“发送命令前后”的窗口内，且与 `s2500 time` 同一时间基（误差主要是 PLCA 等发送时机 + 串口 0.25 s 轮询）。
* **异常**：TSC 字段 1/2/3 都写进了 TTSCC（STATUS0 恒为 TTSCAC=bit10），
  TTSCA(0x10/0x11)、TTSCB(0x12/0x13) 始终 0。已排除“没开 FTSE”“TSC=0”“读寄存器地址错”三种原因
  （同一命令在 C 下稳定可读、值随时间变化）。判断是**数据头 TSC 位域位置与数据手册/本仓库
  `docs/03_spi_protocol.md`（bit7:6）不一致，或本芯片只实现 C 寄存器**；需示波器抓 SPI 头或找 FAE 确认。
  确认前：**发送时间戳只能读 TTSCC**。

## 2. TC14 拓扑发现

### 2.1 先复现“全 0”：不是预期行为，是用法不对

BEACON 仍开、只在一端执行 `s2500 td ref 8`：

```
$ s2500 td ref 8
TD: dur=8 ms dist_mr=0 dly_mr=0 mndly_mr=0 mndly_dur=1 err(dm=0 dly=1 auto=0)
TD_STAT = 0x00004000   # DLYM_ERR
```

**DLYM_ERR** = 内部延时测量期间总线有活动。数据手册 TC14 明确要求：
> all nodes shall stop transmission, and the PLCA coordinator shall stop transmitting the BEACON before TD is started.

所以 TC387 之前的“全 0”是**总线没静默/没配成对端**，不是芯片不支持。

### 2.2 `s2500 td` 封装命令：已修等待逻辑，但仍有稳定性问题

静默总线下按“meas 先起、ref 后起”跑封装命令（dur=16）：

```
[ref HPM] TD: dur=16 ms dist_mr=0 dly_mr=38026 mndly_mr=37840 mndly_dur=16 err(dm=0 dly=0 auto=0)
```

`dly_mr` 已出、`dist_mr=0`：`s2500_td_run()` 的轮询条件把 `DLYM_DONE` 也算“结束”，
自动模式在内部延时阶段结束时就返回并把 `TD_CTRL` 清零，**距离阶段被掐断**。
2026-11-20 已修（`common/s2500/s2500.c`、`s2500_shell.c`、`s2500.h`）：auto 模式改为等 **DM_DONE/DM_ERR**（不再等 DLYM_DONE），读结果前再补 **2*DM_DUR+10 ms** 稳定期；`dly` 模式改为真正触发 `DLYM_START`。修复版实测（HPM meas / TC387 ref, dur=16）：

    [HPM meas]  TD: dur=16 ms dist_mr=319 dly_mr=37988 mndly_mr=0     mndly_dur=1  err(dm=0 dly=0 auto=0)
    [TC387 ref] TD: dur=16 ms dist_mr=0   dly_mr=37938 mndly_mr=37989 mndly_dur=16 err(dm=0 dly=0 auto=0)

`dly_mr` 已正常（约 37900），但 `dist_mr` 仍不对（319/0，正常应约 18750）——说明 **DM_DONE 在本芯片上早于距离阶段真正结束置位**；且后续复测时两块芯片在封装命令的阻塞轮询期间复位（CONFIG0→0x06、PLCA off），无法稳定复现。结论：**自动测距仍建议用手动寄存器序列（2.3 节）**，封装命令可作 `dly`/快速探测用。

### 2.3 手动寄存器流程（本次采用）

```
# 停 BEACON 静默
# 被测节点先起: TD_CTRL = 0x8E80 (dur=8ms) / 0x9E80 (dur=16ms)   [EN|DM_DUR|AUTO_START, REFN=0]
# 0.3 s 后参考节点: TD_CTRL = 0xCE80 / 0xDE80                      [再加 REFN=bit14]
# 等 ~0.5 s, 读 TD_STAT(0xCE01) 应为 0xA000 (DLYM_DONE|DM_DONE)
# 读 DIST(0xCE02/03) DLY(0xCE04/05) MNDLY(0xCE06/07) MNDLY_DUR(0xCE08)
# 两端写 TD_CTRL=0 退出, 恢复 BEACON
```

### 2.4 实测结果（dur=16 ms）

| 方向 | 角色 | TD_STAT | DIST_MR | DLY_MR | MNDLY_MR | MNDLY_DUR |
| --- | --- | --- | --- | --- | --- | --- |
| TC387 meas / HPM ref | ref(HPM) | 0xA000 | 18790 | 38099 | 37897 | 16 ms |
| | meas(TC387) | 0xA000 | 18791 | 37896 | 0 | — |
| HPM meas / TC387 ref | ref(TC387) | 0xA000 | 18749 | 37878 | 37977 | 16 ms |
| | meas(HPM) | 0xA000 | 18749 | 37975 | 0 | — |
| TC387 meas / HPM ref（复现） | ref(HPM) | 0xA000 | 18753 | 38026 | 37820 | 16 ms |
| | meas(TC387) | 0xA000 | 18754 | 37818 | 0 | — |

原始寄存器（TC387 meas / HPM ref，dur=16）：

```
HPM(ref)    : CE00=0xDE00 CE01=0xA000 CE02=0x4966 CE04=0x94D3 CE06=0x9409 CE08=0xF000
TC387(meas) : CE00=0x9E00 CE01=0xA000 CE02=0x4967 CE04=0x9408 CE06=0x0000 CE08=0x0000
```

### 2.5 怎么读这些数

* `DIST_MR` = 距离阶段收到的脉冲数；`16 ms / 18750 ≈ 853 ns` 是“一次往返（含两端内部延时）”。
* `DLY_MR` = 内部延时阶段脉冲数；`16 ms / 37950 ≈ 421 ns` 是单端内部延时。
* 按数据手册 eq.1/eq.2 反推：`tTOF ≈ (853 - 421 - 421)/2 ≈ 5.5 ns`，
  即两端之间单程传播时间约 **4.6–5.5 ns**；按 5 ns/m 估算约 **0.9–1.1 m**（与台面接线长度同量级）。
  绝对距离受 MDI 延时估计误差影响，**不能当卷尺用**，但重复性很好（三次 DIST_MR 18749–18754，±0.03%）。
* **P2MP 共享总线的含义**：TC14 测的是“参考节点 ↔ 被测节点”这一对的传播时间，
  不是整个 segment 的长度；总线上第三个节点如果还在发帧/BEACON 就会让 DLYM_ERR/DM_ERR。
  多分叉时结果里还包含支线 stub 的反射，需按拓扑解释。

### 2.6 副作用（重要坑）

TD 实验（尤其是长时间关 BEACON + 反复启停 TD）之后，**两块板的 S2500 都回到了上电默认态**：

```
CONFIG0 = 0x00000006  [SYNC=0 ZARFE=0]      # 正常应为 0x00009806
PLCA    : en=0 id=255 ncnt=8 PST=0          # 正常应为 en=1 id=2/4
PHY STATUS link=0                            # ping 100% 丢包
WS_STATUS1=0x2000 (RST_IN=0)
```

但 MCU 的 lwIP/shell 仍在跑。用板端 shell 的 `reboot`（MCU 软件复位，会重新拉 RST_N 并重新配置）恢复：

```
$ reboot
[BOOT] ... PLCA : id=2 ncnt=8 en=1
# 之后 s2500 info: CONFIG0=0x9806, PLCA id=2 PST=1, ping 通
```

**规程**：做 TD/HDD 等“静默总线”实验前先记录 `s2500 info`；结束后必须再读一次，
发现 `SYNC=0 / id=255` 立刻 `reboot`。不要用 `s2500 reg 0 3 1` 软复位后不重新配置。

## 3. DIO / LED

命令：`s2500 led <fn0> <fn1>`，读回 `s2500 reg 12 0x0012`（DIOCFG0）。

| 命令 | DIOCFG0 | 解码 |
| --- | --- | --- |
| 上电默认（固件 `s2500_dio_defaults`） | 0x0000CBDF | DIO0.FN=15, DIO1.FN=5, PEN=1, VAL=1 |
| `s2500 led 15 5` | 0x00008B9F | FN0=15, FN1=5（`led` 命令把 PEN 清 0） |
| `s2500 led 5 15` | 0x00009F8B | FN0=5, FN1=15 |
| `s2500 led 8 12` | 0x00009991 | FN0=8, FN1=12 |
| `s2500 led off` | 0x00008181 | FN0=FN1=0（高阻/关闭） |

功能码（数据手册 Table 11）：

* `0xF` LED TX&RX：有数据帧收发时 10 Hz 翻转（不含 BEACON）→ **黄 ACT 有流量时闪**；
* `0x5` LED PLCA Status：电平跟随 PST → **绿 LINK 在 PLCA 同步（PST=1）后常亮**；
* `0x8` CLK25M：DIO 输出 25 MHz 时钟（可用示波器验证）；
* `0xC` BCN：收到 BEACON 时输出约 1.5 ms 脉冲；
* `0x0` Disable：高阻。

本板 DIO 高电平点亮（VAL=1）。**未能拍照**，只做了寄存器回读 + 数据手册功能对照；
建议交付时目视确认绿 LINK 常亮、黄 ACT 随 ping 闪烁。

## 4. SQI / HDD 四板汇总

### 4.1 SQI（`s2500 sqi`）

| 板 | 空闲 | 并发 ping 时 | SQI+（忙） | 备注 |
| --- | --- | --- | --- | --- |
| HPM5361 10.12 | 0/7 | 3/7 | 119/255 | 空闲无流量不更新，属正常 |
| TC387 10.14 | 0/7 | 3/7 | 119/255 | 同上 |
| S32K312 10.13 | 0/7 | 3/7 | 119/255 | 同上 |
| RK3506 10.15 | — | — | — | **受限**：Linux 驱动未暴露 SQI/HDD 接口，无 `s2500` shell |
| STM32F407 | — | — | — | **不可用**：SWD 无法连接（历史问题），未烧写 |

三块 S2500 板读数完全一致，说明 SQI 是链路级统计、与 MCU/SPI 无关。

### 4.2 HDD（`s2500 hdd`，停 BEACON 后静默测）

| 板 | valid | ready | SHORT_OPEN | 1W_SHORT | 解释 |
| --- | --- | --- | --- | --- | --- |
| HPM5361 | 1 | 1 | 2 (SHORT/多余终端) | 1 | 多板并联 49.9Ω 终端过量 |
| TC387 | 1 | 1 | 2 | 1 | 同上 |
| S32K312 | 1 | 1 | 2 | 1 | 同上 |
| RK3506 | — | — | — | — | 驱动未暴露 |

**结论**：HDD 功能本身工作（valid=1、能分类故障），报 `SHORT_OPEN=2` 是**台面多板并联端接过量**
（每块板自带 2×49.9Ω），不是芯片坏；要验证“无故障=0”需只保留总线两端终端后复测。

## 5. 复现命令片段

```bash
# TC6 时间
./tools/s25.py --auto hpm -c "s2500 time" -c "s2500 time set 1000 0" -c "s2500 time"

sleep 0.3
./tools/s25.py --auto hpm   -c "s2500 reg 4 0xCE00 0xDE80"      # ref 后起

# 读完两端 TD_CTRL=0 退出; 若 info 显示 SYNC=0/id=255 -> 板端 reboot
```

## 6. TC10 睡眠/唤醒：未实测（风险控制）

**本次没有让任何芯片进入 Sleep**：共享台面上还有别的测试，睡死后 SPI 不可用，只能靠 RST_N/上电恢复；
虽然 HPM 的 `reboot` 是 MCU 侧命令（不依赖 SPI）理论上可用，但没有在睡死状态下验证过，
按“不冒险变砖”原则留到专门窗口做。

建议的安全步骤：

1. 只用 HPM（RST_N=PA10 由 MCU GPIO 控制，板端 `reboot` 可拉复位）；
2. 进入前记录 `s2500 info` / `WS_STATUS1` / `WS_CTRL1`；
3. 先配 `WS_CTRL1`（WFWD/WDEB/LWTH），再 `s2500 sleep`，同时主机 `ping` 观察中断；
4. 唤醒三选一：另一块板 `s2500 sleep wake`（发 wake tone，需 LCTL=1）、主机 ethtool/驱动 wake tone（当前驱动未暴露）、
   WAKE 引脚脉冲（SW1）；
5. 无论是否唤醒成功，立即 `s2500 info` 读 `WS_STATUS1.WUT/WPIN` 和复位原因；
6. 失败就板端 `reboot`（MCU 复位 → RST_N → 芯片重新初始化），仍不行再断电/重烧；
7. 唤醒后 `WS_CTRL1` 必须重新配置（数据手册明确要求）。
